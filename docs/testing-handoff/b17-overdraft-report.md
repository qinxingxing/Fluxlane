# B17 余额穿透（Underfunded Concurrency Overdraft）测试报告

- **日期**：2026-08-25
- **入口**：`https://run.fluxlane.ai/v1/chat/completions`（生产 CLB，双 RUN 共享状态）
- **测试账号**：`qinxingxing-test`（user id 4，group `default`，走钱包）
- **模型**：`qa-mock-model`（QA Mock 上游，`43.160.247.94:18080`）
- **结论**：穿透存在但可控，预消耗配额 200000 下残留敞口 **<$1/次爆发** → **Accepted-Risk / 有条件 Go**

> 说明：本报告为测试交接材料。按项目约定，`docs/testing-handoff/` 下的交接文档不作为生产代码，仅用于评审留档。

## 1. 背景与目的

验证「用户余额只够 N 次、并发远大于 N」时，平台是否会先调用上游、事后才发现没钱，造成真实损失。

计费为两段式：**预扣**（请求前按预消耗配额冻结额度，够则放行，不够 403 且不调上游）→ 调上游 → **结算**（按上游真实 usage 多退少补）。穿透成立的必要条件是**实扣 ≥ 预扣**，否则多扣部分会在结算时退回，余额回正。

## 2. 测试参数

| 项 | 值 |
| --- | --- |
| 单价 | 输入 $0.2/M、输出 $0.4/M（`model_ratio 0.1`、`completion_ratio 2`） |
| 预消耗配额 | 200000 → 单次**预扣 ≈ $0.04** |
| Mock 实报用量 | `prompt_tokens=200000, completion_tokens=100000` → 单次**实扣 = $0.08** |
| 起始钱包 | 每轮重置 **$0.20**（够 5 次预扣） |
| 发压方式 | 单机并发直打 CLB；禁止 `--resolve` 钉死单节点 |

为触发穿透机制，特意让实扣（$0.08）> 预扣（$0.04）。生产真实流量下实扣 ≈ 预扣，敞口更小（见第 7 节）。

## 3. 实测数据

| 并发 | 抢过预扣（HTTP 200） | HTTP 403 | HTTP 429 | 结算后钱包 | 透支 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | **8** | 12 | 0 | −$0.44 | **$0.44** |
| 50 | 7 | 43 | 0 | −$0.36 | $0.36 |
| 100 | 5 | 95 | 0 | −$0.20 | $0.20 |
| 200 | 6 | 194 | 0 | −$0.28 | $0.28 |

账目自洽（以 N=20 为例）：8 × $0.08 = $0.64 实扣；$0.20 − $0.64 = **−$0.44**。被拒请求报出 `剩余额度 $-0.12`，证明负余额被并发脏读。

## 4. 关键规律

1. **抢过笔数被封顶在 ~5–8**，不随并发增长（20→8、50→7、100→5、200→6）。瓶颈是**共享 Redis 异步扣减的时间窗**，不是并发数。
2. **透支深度 ≈ 抢过笔数 × 单次实扣 − 钱包**，随单次成本线性放大。
3. 钱包被打负后，后续预扣立即 403 → **同一次充值只能被穿一次**。

## 5. 根因（代码层）

- 预扣判额 `service.NewBillingSession → tryWallet` 调 `model.GetUserQuota(userId, false)`，从**共享 Redis** 读余额，判断 `余额 − 预扣 < 0` 才 403；
- 扣减 `model.DecreaseUserQuota → cacheDecrUserQuota → RedisHIncrBy` 为 **`gopool.Go` 异步 fire-and-forget**；
- **读—判断—扣减非原子**，且扣减异步 → 并发在扣减落地前读到同一正余额 → 全判定「够钱」放行；
- 钱包扣减为无下限 `quota - N`，**无 `WHERE quota >= N`、无行锁**（订阅路径才有 `lockForUpdate`）。

## 6. CLB 影响：不放大

- 余额存在**同一份共享 Redis 哈希**，两台 RUN 非「各持一份余额」（`GetUserQuota`→Redis，`DecreaseUserQuota`→`RedisHIncrBy`）。
- 抢过笔数随并发**收敛**而非发散——若各节点独立记账应越打越穿。
- 敞口由异步扣减窗口决定，**与节点数无关**。

**局限**：单机发压，~8 为**保守下限**；分布式协同爆发能压紧到达时间，抢过笔数可能更高。单节点 vs CLB 铁证需从跳板机内网直连单台 RUN（内网 `10.20.1.15` / `10.20.2.11`）打并发对比，本次未做（云端 agent 直连两台 RUN 公网 IP 均超时）。

## 7. 风险评估与缓解

| 预消耗配额 | 单次预扣 | 与贵价实扣差额 | 单次爆发最大穿透 |
| ---: | ---: | --- | ---: |
| 2000（旧） | ≈$0.0004 | 巨大 | **~$40** |
| 200000（现行） | ≈$0.04 | 接近真实成本 | **<$1** |

调大预消耗配额把「预扣」抬到接近多数请求的真实成本，使抢过的请求即便结算也不产生大额超支，从而把残留敞口压到 <$1。经风控确认为**已知可接受风险**。

## 8. 判定与前提

- **判定**：Accepted-Risk / 有条件 Go（非 No-Go）。
- **前提**：
  - **不得调小预消耗配额**（保持 ≥ 200000）；任何调小都会重新放大透支，回退到 No-Go 口径。
  - 敞口随**单次实扣**线性放大，贵价模型需单独关注。
- **可选彻底加固**：预扣改为原子条件扣减
  `UPDATE users SET quota = quota - N WHERE id = ? AND quota >= N`
  （受影响行数=0 即余额不足 403），消除穿透后可恢复「余额不穿透」为硬门禁。

## 9. 复现步骤

前置：测试账号 API Key（无限额，走钱包）、面板访问令牌（读余额/日志）、`qa-mock-model` 实报 200000/100000、钱包重置 $0.20。

```sh
# 读余额（面板令牌）
curl -s -H "Authorization: Bearer $DASHBOARD_ACCESS_TOKEN" \
  https://api.fluxlane.ai/api/user/self | jq '.data.quota/500000'

# 20 并发打 CLB（测试 API Key）
for i in $(seq 1 20); do
  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: Bearer $TEST_API_KEY" -H 'Content-Type: application/json' \
    -d '{"model":"qa-mock-model","stream":false,"max_tokens":8,"messages":[{"role":"user","content":"pong"}]}' \
    https://run.fluxlane.ai/v1/chat/completions &
done; wait

# 等结算后再读余额，HTTP 200 数 × $0.08 − 起始余额 = 透支
sleep 10
```

统计：HTTP 200 数即抢过预扣的请求数；结算后余额为负即穿透。

## 10. 测试后收尾

1. 钱包 `qinxingxing-test` 从负值重置回正常值。
2. `qa-mock-model` Mock 实报用量改回 **10000 / 2500**，避免该渠道后续按 $0.08 误计费。
